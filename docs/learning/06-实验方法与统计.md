# 06 实验方法与统计

## 你需要先知道

项目现在有四种不能混用的时间：V5 cold process、V7 setup、V7 resident request
和profiler运行时间。论文主要比较V7 request，并单独报告setup和摊销。

## 核心原理

V7每组先建立一次session，做3次warmup，再测10次request。每个规模有18组配置，
因此是54次预热、180次正式请求。中位数表示典型请求，p95观察尾部。若setup为
$T_s$、请求中位数为$T_q$，$n$次请求的估计均摊成本为$T_s/n+T_q$。

结果hash用于快速发现后端差异，oracle再用精确整数逐行核对。失败记录不能静默
删除；证据bundle还绑定matrix、命令、二进制、Git commit、GPU UUID、数据
manifest和逐文件checksum。

## 代码入口

- V7矩阵：`experiments/v7_formal_sf1.yml`、`v7_formal_sf10.yml`
- 会话runner：`scripts/run_v7_benchmarks.py`
- schema与统计：`scripts/v7_benchmark_schema.py`、`summarize_v7_records.py`
- 证据审计：`scripts/v7_evidence_bundle.py`

## 自己检查

为什么SF10 best hybrid请求10.054 ms，却不能说“一次查询只要10 ms”？

**检查答案：** 其setup约4997.298 ms；只请求一次时摊销约5007.352 ms，100次
后约60.027 ms。要说明数据是否已经常驻以及重复次数。

## 老师可能追问

setup为什么只测一次？当前每组只创建一个session，这是实验缺陷。request有10个
样本，但setup没有分布，摊销值对一次性抖动更敏感，论文已经把它列为限制。

## 一分钟复述

SF1和SF10各有18组配置、54次预热和180次正式请求，全部通过oracle。论文从
raw记录生成中位数、p95、setup和摊销值，不手工挑最好一次，也不把profiler
时间当作普通延迟。
